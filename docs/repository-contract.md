# Контракт для интеграции слоёв

## Модели и БД

Ветка backend объединена с main. Используются PostgreSQL и репозитории из
пакета repository.jdbc с прямыми Connection, PreparedStatement и ResultSet.
Схема и начальные данные применяются явно из database; автоматическое создание
схемы при запуске отключено. Рабочая БД не заменяется тестовой H2.

В Client и FuneralRequest оставлены пустой и полный конструкторы, getters/setters.
equals и hashCode не переопределяются. Мапперы создают пустую модель и заполняют
её поля. Для сравнения сохранённых записей используйте ID, для проверки
содержимого — нужные поля.

CeremonyType и RequestStatus используют явные databaseId, совпадающие со
справочниками. ordinal() не используется. Новый ID в справочнике требует
добавления значения в Java enum; неизвестный ID приводит к DatabaseException.

## Репозитории

- create возвращает новую сохранённую модель с ID. Время создания заявки
  формируется БД; переданный объект не меняется.
- update возвращает сохранённую модель и не меняет время создания.
  При отсутствии ID выбрасывается EntityNotFoundException.
- findById возвращает Optional.empty(), если записи нет.
- deleteById для отсутствующего ID ничего не делает. Service предварительно
  проверяет наличие записи, чтобы API мог вернуть 404.
- findByDeceasedName ищет часть ФИО без учёта регистра; %, _ и ! ищутся буквально.
  Поиск по комментарию не выполняется.
- findByClientId выполняет поиск заявок выбранного клиента.
- findFiltered объединяет необязательные статус, тип и границы периода в одном SQL-запросе.
  Границы периода включаются в результат. Порядок дат проверяет Service.
- findAllOrderByCeremonyDate и findAllOrderByPrice принимают ascending.
  При равных значениях используется ID по возрастанию.
- SQLException оборачивается в DatabaseException с сохранением причины и SQLState.

Каждый метод открывает отдельное подключение с автокоммитом. Аннотация
@Transactional сама по себе не объединяет прямые dataSource.getConnection().
Если появится операция из нескольких обязательных SQL-изменений, для неё
потребуется общее подключение и отдельная транзакция.

## Сервисы, DTO и REST

Контроллер передаёт DTO мапперу, затем вызывает сервис. Маппер только копирует
поля. Проверки и нормализация выполняются сервисом через классы validation.
Отдельных копий правил для DTO нет.

ClientService нормализует телефон и обрабатывает нарушение уникальности
(SQLState 23505) как бизнес-конфликт. При удалении клиента нарушение FK
(23503 или 23001) означает наличие заявок; другие ошибки БД не маскируются.

FuneralRequestService задаёт NEW при создании, проверяет клиента, обязательные
поля, цену, дату и три запрещённых перехода статуса. При update сохраняется
исходное время создания. Результаты create/update берутся из Repository.

ID и createdAt отсутствуют в DTO создания. Для клиента используются
ClientRequestDto/ClientResponseDto; для заявки — Create/Update/Response DTO.
HTTP-адреса и правила ввода описаны в README.

Ошибки приложения разделены на ValidationException, EntityNotFoundException,
BusinessException и DatabaseException. ApiExceptionHandler возвращает единый
безопасный JSON: ошибки ввода — 400, отсутствующие записи — 404,
бизнес-конфликты — 409, ошибки БД/вывода файла и непредвиденные ошибки — 500.
Причины технических ошибок остаются в серверных логах.

## Проверки и оставшиеся задачи

Unit-тесты работают без сервера БД. Профиль postgres-it дополнительно запускает
JdbcRepositoriesIT и ApiIntegrationIT в отдельных случайных схемах.
@Transactional для изоляции JDBC-тестов не используется; схемы удаляются после
проверок. Подключение берётся из TEST_DB_URL, TEST_DB_USERNAME, TEST_DB_PASSWORD.

Проверяется цепочка REST → Service → JDBC → PostgreSQL, статистика и экспорт XLSX.
Консольный HTTP-клиент ещё не реализован. При его интеграции нужно использовать
согласованные адреса из README.
