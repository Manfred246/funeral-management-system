# Контракт для интеграции слоёв

Этот документ описывает готовую часть участника 1 и точки подключения для
участников 2 и 3. Согласование с другими участниками команды ещё требуется.

## Модели

`Client` и `FuneralRequest` взяты из локальной ветки `origin/backend` на коммите
`cd24da9`. Проверено: поля и типы соответствуют контексту проекта; SQL, HTTP,
Scanner и бизнес-правил в этих классах нет. Конструкторы и getters/setters сохранены.
Служебное поле `clients.created_at` остаётся в БД, как допускает документ задания.

`CeremonyType` и `RequestStatus` используют явные числовые `databaseId`,
совпадающие со справочниками. `ordinal()` не используется. Добавление новых
значений справочника требует обновления Java enum. Неизвестный ID при чтении
заявки приводит к `DatabaseException`.

Репозитории из `origin/backend` не переносились: они используют `JdbcTemplate`.
В текущей реализации видны `Connection`, `PreparedStatement`, `ResultSet`
и `try-with-resources`, как требует задание.

## Методы репозиториев

- `create` создаёт запись и возвращает новую модель с ID из БД.
  Переданный объект не изменяется; Service должен использовать результат метода.
  Это не upsert. Время создания заявки также берётся из БД.
- При создании заявки отсутствие статуса означает `NEW`. Service должен
  явно задавать начальный статус и проверять правила создания заявки.
- `findById` возвращает `Optional.empty()`, если записи нет.
- `update` возвращает сохранённую запись; время создания не изменяется.
  Если ID не найден, выбрасывается `EntityNotFoundException`.
- `deleteById` для отсутствующего ID ничего не делает. Если API должен вернуть
  404, проверку выполняет Service. Удаление клиента с заявками запрещено FK.
- `findByDeceasedName` ищет часть ФИО без учёта регистра. Символы `%`, `_`, `!`
  ищутся буквально. Пустая строка возвращает все заявки.
- `findByClientId`, `findByStatus`, `findByCeremonyType` выполняют поиск и фильтры в SQL.
- `findAllOrderByCeremonyDate(true)` и `findAllOrderByPrice(true)` сортируют по
  возрастанию; `false` — по убыванию. При равных значениях используется ID по возрастанию.
  Пользовательское имя столбца в SQL не попадает.

Service передаёт непустые модели, нужные enum и ID; проверка ввода и бизнес-правил
остаётся в Service. Репозиторий дополнительно опирается на ограничения БД.
`SQLException` превращается в `DatabaseException`; причина сохраняется для логов,
SQLState доступен через `getSqlState()`. Текст SQL и stack trace не следует выдавать
клиенту. Участнику 3 нужно добавить обработку этих исключений в REST-слое.

## Подключение остальных слоёв

В Service внедряется интерфейс `ClientRepository` или `FuneralRequestRepository`.
Spring автоматически найдёт JDBC-реализации с `@Repository` и передаст им `DataSource`.

При переносе сервисов из `origin/backend` нужно заменить `save` на `create`,
обработку `DataAccessException` — на `DatabaseException`, а поиск, фильтрацию
и сортировку через Java Stream — на соответствующие методы Repository.

Каждый метод открывает своё подключение с автокоммитом. Пока операций,
требующих нескольких SQL-запросов в одной транзакции, нет. Если они появятся,
нужно отдельно согласовать передачу общего Connection: одна аннотация
`@Transactional` не объединит прямые вызовы `dataSource.getConnection()`.

Проверены создание Spring-контекста, запуск HTTP-сервера и работа репозиториев
через Spring с настоящим PostgreSQL. Полная цепочка Console → REST → Service →
Repository требует готовности слоёв участников 2–4. REST CRUD, статистика,
экспорт и бизнес-правила не реализуются вместо них в рамках этой задачи.
